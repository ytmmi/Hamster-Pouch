# RFC 0001：文件身份与哈希一致性策略

状态：正式草案。已确认方向：内容哈希负责文件身份，感知哈希只负责相似/重复检索。

## 背景

媒体源是真实本地文件夹。用户可能在软件外移动、重命名、修改或替换文件；也可能发生同名替换。文档明确要求：每个文件一个索引，并以哈希等方式校对，防止“文件已更改但同名”。

## 决策

1. 图像身份以内容哈希为准。
2. 文件大小、mtime、路径只用于快速发现“可能变化”，不作为身份。
3. 感知哈希用于相似图、重复图、检索辅助，不参与身份判断。
4. 哈希结果必须记录算法名和算法版本，允许未来迁移。
5. 图像在媒体源间剪切/复制后，只要内容哈希一致，当前仓库内的 tag、评分、相册成员关系不丢失。

## 核心规则

### 扫描入库

- 新文件：读取内容并计算内容哈希；写入文件索引。
- 音频文件（D11）：仅写占位行（`media_type=audio`），不计算内容哈希/缩略图；后续开放音频索引时原位升级。
- 未知类型文件（D11）：跳过，不进入文件索引。
- 已索引文件：先比较 size/mtime；若未变化，可标记为快速通过；若变化或处于校验队列，则重算内容哈希。
- 内容哈希变化：视为同一个路径上的新内容；是否保留历史索引关系属于实现期开放点，不影响身份规则。

### 移动/重命名识别

- 路径变化但内容哈希一致：更新路径，不重置 tag、评分、相册成员。
- 内容哈希一致但出现在多个路径：标记为重复文件候选；是否自动合并属于实现期开放点，不影响身份规则。
- 路径存在但内容哈希与索引不一致：进入“已变更”状态，触发元数据、缩略图、感知哈希重建。

### 失效与校对

- 文件无法读取：标记 `missing` 或 `unreadable`，不立即删除索引。
- 文件恢复且内容哈希一致：恢复正常状态并保留仓库内数据。
- 文件恢复但内容哈希不同：按新内容处理；旧数据是否保留为历史版本属于实现期开放点，不影响身份规则。
- 后台校验：watcher 实时监听负责快速发现变化，定期全量校验负责兜底；watcher 事件丢失或溢出时必须触发局部或全量重扫。

## 数据约束

每条文件索引至少包含：

- 稳定文件 ID。
- 当前媒体源 ID。
- 当前相对路径。
- 内容哈希、内容哈希算法、内容哈希算法版本。
- 感知哈希、感知哈希算法、感知哈希算法版本。
- size、mtime、扫描时间、校验状态。
- 软删除/缺失状态。

例外（D11）：音频占位行不计算哈希，`content_hash`/`perceptual_hash` 可空，`verify_status=placeholder`；媒体类型判定为扩展名优先 + 内容兜底。

## 风险

- 全量内容哈希首次扫描成本高；需要任务队列、暂停/恢复和进度事件。
- 大文件重复读取会影响磁盘占用；扫描器必须限速并可取消。
- 感知哈希不能反向证明同一文件，因此禁止参与身份合并。

## 实现期开放点（非架构决策）

- 内容哈希算法：BLAKE3 / SHA-256 / 其他。
- 感知哈希算法：pHash / dHash / aHash / 多算法并存。
- 同名替换后是否保留旧内容的“历史版本”记录。
- 重复文件候选是否允许跨媒体源自动合并显示。
