# RFC 0005：视频与媒体能力决策

状态：正式草案。本文记录用户已确认的视频播放、元数据、缩略图与色彩参考方向；实现期开放点不得反向修改这些决策。

## 已确认决策

1. 视频播放：libmpv 全格式播放，运行在独立媒体子进程；子进程单实例常驻，崩溃自动重启；播放画面嵌入面板（原生渲染目标随面板布局自由组合/停靠/调整）。
2. libmpv 与 ffmpeg/ffprobe 随应用捆绑发布（不依赖用户系统环境）；外部 CLI 程序统一放置于顶层 `external-cli/` 目录（当前含 `ffmpeg/`，后续其他外部编解码程序同目录）。
   > **落地说明（2026-10）**：捆绑由打包脚本承担——`tools/package-build.mjs` 把 `external-cli/ffmpeg/`
   > 复制到包内 **exe 同级**，只带**运行时子集**（`bin\` 下两个 exe + 全部 DLL + `LICENSE.txt`；
   > `ffplay.exe` / `doc` / `include` / `lib` / `presets` 不带，省约 31 MB）。
   > `bin\` 下的 DLL **一个都不能省**：两个 exe 按 PE 导入表静态绑定全部 av* DLL，实测去掉
   > `avdevice-62.dll` 连 `-version` 都跑不起来（`0xC0000135`）。因此子集规则只写"排除明确不需要的条目"，
   > 不写"只保留某几个 DLL"的白名单——上游升级新增 DLL 时白名单会静默漏掉。
   > 门禁：`pnpm check:bundled-runtime`。
   > **libmpv（mpv.exe）同样随包分发（可选资产，2026-10）**：`external-cli/mpv/`（约 119 MB）
   > **存在则入包、缺失则跳过并说明**。之所以是可选项而非必需项：该目录**不入 git 库**
   > （100 MB+ 二进制不进版本库，`.gitignore` 忽略），因此**新克隆里必然没有它**，
   > 做成硬失败会让 `pnpm app:build` 在新克隆上直接断掉。
   > **"不入库"与"能否进构建包"是两件事**——打包脚本从**本地磁盘**复制、不读 git，
   > 本机有 mpv 就会进包。mpv 整目录原样入包（**不裁剪**：`mpv.exe` 的 IPC 能启动
   > 不证明视频渲染不需要 `d3dcompiler_43.dll`，D3D11 输出编译 shader 用它，证据不足不裁）。
   > 注：播放器面板当前走 DOM `<video>`、libmpv 路径休眠（见下方「媒体子进程模型」），
   > 即产品界面暂不调用 mpv；入包是为该路径复活时不再缺件，需要时仍可用 `HP_MPV_BIN` 覆盖。
3. 视频元数据：全量媒体信息（时长、分辨率、编码、帧率、码率、音轨、字幕、章节）；由 ffprobe 外部进程探测；元数据为独立面板，按仓库布局自由组合。
4. 视频缩略图：扫描时同步生成首帧缩略图，由 ffmpeg 外部进程批量抽帧；视频感知哈希复用首帧图像哈希（见 RFC 0001 与 D12）。
5. AI 打标第一期仅图片；视频 AI 打标延后（D17）。
6. 色彩参考：自动提取调色板 + 手动调整/锁定色值；浏览时按需提取并缓存；仅图片，视频不做色彩参考（D18）。
7. 媒体能力统一由 `hp-media` crate 承载（D19）。

## 媒体子进程模型

> **2026-09 决策更新（覆盖本条绝大部分内容）：播放器面板改用 DOM `<video>`**。
> libmpv 原生窗口嵌入在真机上反复暴露两类硬伤——(1) Win32 原生窗口**永远盖在 WebView
> 之上**，打开「全部设置」等 DOM 浮层时视频漂浮在浮层上方（用户判为"没内嵌进面板"）；
> (2) 点击要么被原生窗口吞掉（`HTTRANSPARENT` 只转发同线程窗口，WebView2 输入窗口不保证
> 同线程）、要么依赖后端广播链路，真机反复不可靠（用户判为"单击无任何效果"）。
> 用户明确要求**参考查看器的视频部分**（查看器用 DOM `<video>`，天然内嵌、被浮层自然
> 覆盖、点击由浏览器原生派发）。因此播放器面板改为与查看器同构的 **DOM `<video>`**：
>
> - 蓝图双击视频（`payload.play`）→ `playerPlayStore.requestPlayerPlay(fileId)` →
>   面板解析路径、`convertFileSrc` 加载并自动播放；不再启动 mpv 子进程。
> - 单击画面 = 暂停/继续：直接读写 DOM 元素实时的 `.paused` / `play()` / `pause()`，
>   无状态过期、无点击转发问题。
> - 切标签自动暂停、播放完成回到首帧暂停、进度条全部由 `<video>` 元素事件驱动。
> - `media.*` 命令、`hp-media::MediaProcess`、`embed_window.rs` **保留但处于休眠**
>   （命令层与测试仍在，面板不再调用）；后续若需 libmpv 再评估，勿在本决策外复活。
> 下文原「渲染子窗口」各条均为**已退役路径的记录**，供历史追溯。

- 形态：独立子进程，承载 libmpv；单实例常驻，应用生命周期内共享。
- 崩溃隔离：损坏/恶意视频导致播放崩溃不带走主程序；子进程崩溃自动重启。
- 渲染：渲染目标挂到面板容器的原生子窗口，随面板移动/缩放；面板关闭时释放句柄。
- **渲染子窗口的显隐跟随面板可见性（2026-09 补充，已随 DOM `<video>` 方案退役）**：它是 Win32 原生窗口，**不随 WebView 里面板的隐藏或卸载而消失**。面板切到后台标签（或关闭）时必须显式隐藏/销毁，否则会以不透明背景盖住面板原区域（"视频没了但一块区域点不动"）。
- **渲染子窗口不得盖住应用级浮层（2026-09 真机修正，已退役）**：Win32 原生窗口**永远盖在 WebView 之上**，打开「全部设置」这类全窗口 DOM 浮层时若仍显示渲染子窗口，视频会漂浮在浮层上方。曾以 `appOverlayStore` 广播浮层开合、面板订阅后隐藏/恢复渲染子窗口。
- **点击由渲染子窗口自收（2026-09 真机修正，已退役）**：曾把 `WM_NCHITTEST → HTTRANSPARENT` 命中测试穿透改为渲染子窗口自收点击（`WM_LBUTTONUP` 广播 `media.surface.click`），面板监听后调 `media.togglePause` 原子切换。
- **单击切换必须原子（2026-09 真机修正，已退役）**：曾要求 `media.togglePause` 在后端一次锁内完成「读 pause → 取反写入」，避免并发点击读到相同旧值、发出两次相同暂停。DOM `<video>` 方案下该问题天然不存在。
- **面板内不显示单击提示文字（2026-09 用户裁决，仍有效）**：画面区不显示「单击暂停/播放」等覆盖提示，也不设悬停提示；单击交互仅靠行为本身表达。
- **加载即播放（2026-09 真机修正，已退役）**：曾因 mpv 的 `pause` 属性跨文件保留而在 `load_file` 后显式复位 `pause=false`；DOM `<video>` 每次换源自动从开头播放。
- **切标签默认自动暂停（2026-09 用户裁决，仍有效）**：切到其它标签**自动暂停**正在
  播放的视频；是否自动暂停可在「全部设置 → 面板 → 媒体播放器」的「切换标签时自动暂停」
  开关控制（默认开）。切回时**不自动继续**：画面保持暂停帧，单击画面才继续。关闭自动
  暂停时切标签不停播（DOM 视频在后台标签继续播放，切回即继续显示）。
- **播放完成回到首帧暂停（2026-09 用户裁决，仍有效）**：`<video>` 的 `ended` 事件触发时
  把 `currentTime` 归零并 `pause()`——回到首帧并暂停；再次单击画面即从 0:00 继续。
- **播放器面板交互（2026-09 用户裁决，仍有效）**：面板**不放**播放/暂停/定位/停止按钮；
  **单击画面 = 暂停 / 继续**（DOM 元素实时状态，见上），画面下方一根**进度条**（可拖动
  定位，并实时同步播放进度）。进度来自 `<video>` 的 `timeupdate` / `loadedmetadata` 事件，
  面板不得以"自己发起过播放"判断会话状态——蓝图双击是宿主直接发起播放的。
- **首次播放必须内嵌（随 DOM `<video>` 方案天然满足）**：DOM 元素永远在面板内，不存在
  "渲染目标未就绪弹独立窗口"的时序竞争（`docs/issues/0001` 的根因 1–6 一并消除）。
- **IPC 管道的两条硬约束（2026-09 实测，`media.*` 命令层仍遵守）**：mpv 的命名管道
  **只有一个句柄可用**（第二次 `open` 直接 `ERROR_PIPE_BUSY`），且**同一句柄上的阻塞读会挡住写**。
  因此读取**必须非阻塞**（`PeekNamedPipe` 探明可读字节后再读），绝不能让一个线程常驻阻塞读、
  另一个线程写命令——否则表现为"第一次播放正常、之后每次播放/取进度都永久挂起"。
  宿主侧所有 `media.*` 命令也必须 `async`（Tauri 的普通 `fn` 命令在主线程执行，阻塞即卡界面）。
- 主进程与媒体子进程通过宿主定义的 IPC 通信；协议细节属于实现期开放点。

## 图片格式支持边界（2026-10-11）

> 本节登记 **用户 2026-10-11 直接要求**："将 ffmpeg 支持的进行实现，不支持的记录到文档"。
>
> 判定方式是**逐个格式端到端实测**，而不是读 `ffmpeg -decoders` 的清单——两者并不等价
> （见下方 SVG 的反例）。判据是：捆绑 `ffmpeg.exe` **有对应解码器**，**且**走本项目
> **完全相同**的解码管线能真的出图：
>
> ```
> ffmpeg -hide_banner -loglevel error -i <文件> -frames:v 1 \
>        -vf "scale='min(<max_dim>,iw)':-2" -f image2pipe -vcodec png -
> ```
>
> （`crates/hp-media/src/decode.rs` 的 `decode_image_with_ffmpeg`；缩略图 / 调色板 /
> 感知哈希走有界 `max_dim`，查看器预览走不缩放的 `u32::MAX`。）

### 1. 支持矩阵（**四档**，按**解码路径**分而不是按"能不能看"分）

| 档 | 格式 | 解码路径 |
| --- | --- | --- |
| **进程内**（`image` crate 自带解码器） | jpg / jpeg / jfif / png / apng / gif / bmp / webp / tiff / tif / ico / **tga / dds / exr / hdr / qoi / ff（farbfeld）/ pnm / pam / ppm / pgm / pbm** | `image::open`，**不碰 ffmpeg** |
| **进程内 + 兜底**（libheif） | avif / heic / heif | 进程内 libheif（libde265 / aom）；超大图或有界请求走 ffmpeg（尺寸分流，≤ 16 MP 进程内） |
| **进程内栅格化**（`resvg`，D112） | **svg / svgz** | `hp_media::svg` 进程内栅格化（`resvg` + `tiny-skia`），**不碰 ffmpeg**——ffmpeg 对它只有解复用器、没有解码器 |
| **仅 ffmpeg**（进程内无解码器） | jp2 / j2k / jpf / jpx（JPEG 2000）、jxl（JPEG XL）、psd、pcx、sgi、ras（Sun Raster）、dpx、fits、wbmp、xbm、xpm、jls（JPEG-LS）、pfm、**dib** | `FFMPEG_ONLY_IMAGE_EXTS`，直接走 ffmpeg 有界解码 |

**加粗的是 2026-10-11 新收的格式**（此前 13 个 → 2026-10-11 **43** 个 → 2026-10-16 加 `svgz` 后 **44 个**扩展名）。

**为什么 SVG 要单立一档而不是并进任何一档**（D112）：它三个"都不是"——
不是"进程内 `image` 能解"（`image` 没有 SVG 解码器），不是"仅 ffmpeg"（ffmpeg 对 SVG
**没有解码器**，`svg_pipe` 只是解复用器），也不是 libheif 家族。它是**矢量**，
必须进程内栅格化（`resvg`），且**必须绕过 ffmpeg 快路径**：
`preview.get` 在生产里恒传 `Some(ffmpeg)`，"有 ffmpeg 就交给 ffmpeg"的写法会让
SVG 永远走不到栅格化器 —— 表现为 **SVGZ 在查看器里一片空白**
（`svg` 走 Chromium 原生渲染，看不出问题）。由 `svg_preview_ignores_ffmpeg_fast_path` 钉住。

**"仅 ffmpeg"这一档存在的意义**：这些格式此前**既不入库、也没有解码路径**，
于是"捆绑 ffmpeg 明明能解，用户却看不到"。两件事必须**同时**做，缺一即为静默失败：

- 进 `hp-scanner` 的扩展名表 → 文件**入库**；
- 进 `hp-media` 的 `FFMPEG_ONLY_IMAGE_EXTS` → 图**解得开**。

只做前者 = "入库了但显示不可用"；只做后者 = "解码能力白做"。
两者的包含关系由 `pnpm check:panels` 断言（`ffmpeg-only ⊆ 扫描器扩展名表`）。

### 2. 为什么扩容的兜底**只给"进程内没有解码器"的格式**

沿用缺陷 0019 确立的口径：进程内能解的格式（jpg/png/webp/tiff…）**进程内成功或失败都
原样返回**，结果与旧实现**逐位相同**、扫描期 dHash / 调色板缓存可比性不受影响。

给它们也加 ffmpeg 兜底会带来**行为变更**：坏文件从"报错"变成"被 ffmpeg 抢救成功"。
这由回归用例 `non_avif_failure_is_not_swallowed_by_ffmpeg` 钉住。

而"仅 ffmpeg"那档此前**从来没有解码成功过**（`image::open` 返回 `Unsupported`），
不存在需要保持兼容的旧缓存，因此直接走 ffmpeg 是安全的。

### 3. 内容兜底（改名文件）只收**签名可靠**的格式

`hp-scanner` 的 `sniff_media_type` 为下列新格式补了 magic bytes 兜底（改名的文件也能入库）：
`8BPS`（PSD）、`DDS `、`76 2F 31 01`（EXR）、`qoif`、`farbfeld`、`#?RADIANCE` / `#?RGBE`（HDR）、
`59 A6 6A 95`（Sun Raster）、`01 DA` + BPC∈{1,2}（SGI）、`SDPX` / `XPDS`（DPX）、
`SIMPLE  = `（FITS）、`/* XPM */`、JPEG 2000 签名盒、JPEG XL（`FF 0A` / `JXL ` 盒）、
Netpbm（`P1`–`P7` **且第 3 字节是空白**）、PFM（`PF\n` / `Pf\n`）。

**刻意不做兜底的**（仍可靠扩展名正常入库，只是改名后认不出）：
`wbmp`（`00 00` 两字节）、`pcx`（`0A` + 版本）、`dib`（`28 00 00 00` 是通用长度前缀）、
`tga`（签名在**文件尾** `TRUEVISION-XFILE`，而嗅探只读头部 16 字节）。
给它们做兜底会把**未知二进制吸进索引**，正是 D11「未知类型不索引」要防的事。

### 4. **不支持**的常见图像格式（本机实测，如实记录）

以下格式**捆绑 ffmpeg 没有解码器**（`-decoders` 查无、或实测解不出），因此本应用
**不索引、不显示**。若要支持，必须引入新解码依赖（属新决策，不在本次范围）：

**当前缺口统计（2026-10-16 复核）：6 类 / 21 个扩展名。**

| 类别 | 扩展名 | 个数 | 说明 |
| --- | --- | --- | --- |
| **相机 RAW** | `dng` `cr2` `cr3` `nef` `arw` `orf` `rw2` `raf` `pef` `sr2` | 10 | ffmpeg **无任何 RAW 静态图解码器**（`-decoders` 里没有 dng / cr2 / …）。需 `rawspeed` / `libraw` 一类库 |
| **JPEG XR** | `jxr` `wdp` `hdp` | 3 | ffmpeg 无解码器；Windows 有系统 codec 但不可依赖（同缺陷 0019 对 WIC 的裁决） |
| **矢量 / 分层工程** | `xcf` `eps` `wmf` `emf` | 4 | ffmpeg 无解码器；且多为矢量 / 分层工程格式，不是位图 |
| **JBIG / JBIG2** | `jbig` `jbig2` | 2 | ffmpeg 无解码器（常见于扫描件 PDF 内部，但那是 PDF 渲染的事，与图片管线无关） |
| **Apple 图标** | `icns` | 1 | ffmpeg 无解码器（`ico` **支持**，走进程内 `image` crate） |
| **WebP 2** | `webp2` | 1 | 实验格式，无解码器 |

> **SVG 已于 2026-10-16 移出本表**（D112）：它此前是这张表里唯一
> "ffmpeg 不解、但也进不了进程内"的格式；现在由 `resvg` 进程内栅格化接管。
> 这个位置值得留意——**它是本表里唯一一个被"补上"而不是"等新依赖"的缺口**，
> 因为矢量栅格化有纯 Rust 实现（`resvg`），而 RAW / JPEG XR 没有。
>
> **本表的判定方式**：逐个扩展名查捆绑 ffmpeg 的 `-decoders`（**并核对解复用器**，
> 防 `svg_pipe` 那类**假阳性**——它在解复用器清单里，却没有任何解码器）。
> 2026-10-16 复核命令与结论：
> `ffmpeg -hide_banner -decoders`（561 个解码器）中，上表 21 个扩展名**一个都没有**
> 对应解码器；`-demuxers` 里也没有它们的条目。
> 注意 **JPEG XL 的解码器名为 `libjxl`**（不是 `jxl`）、**farbfeld 走进程内**
> （`image` crate，不在 ffmpeg 表里）——按扩展名直接 grep 会误判这两个为"不支持"。

> **不登记但同样不支持**：动画 / 多帧序列的容器变体（如动画 HEIC 序列）。
> `preview.get` 与缩略图都只取**单帧**，这是既有口径而非本次缺口。

### 5. 前端取图：白名单取反（2026-10-11，2026-10-16 补 SVG/SVGZ 之分）

`app_ui/shared/previewUrl.ts` 的 `needsPreview` 由**黑名单**（只列 `heic` / `heif`）
改为**白名单取反**（只列 Chromium 原生渲染得了的 11 个扩展名，其余全走
后端 `preview.get`）。

⚠️ **`svg` 在白名单里、`svgz` 刻意不在**（D112）：两者都是矢量，但 Chromium 的
`<img src>` 只认 `image/svg+xml` 的**未压缩**形式（直接解析 XML）；`svgz` 是 **gzip 流**，
浏览器拿到的是二进制而**不是 XML** → 画不出来。所以 `svgz` 必须走后端
（`preview.get` 解压 + 栅格化成 JPEG）。
**这条正是"白名单取反"的失败方向在起作用**：漏了它只是"多走一次后端"，
而不是"画出一片空白"——但**后端那一侧必须真的解得开**（见 §1 的 D112 说明：
`preview.get` 走 ffmpeg 快路径的话，`svgz` 就是一片空白）。

理由是不对称的失败代价：扩容后黑名单会**静默漏项**——新收的 `jp2` / `jxl` / `psd` /
`pcx` / `tga` / `dds` / `exr` / `qoi` / `pnm` 家族 Chromium 一律渲染不了，
漏一个就是**一片坏图**；而白名单漏一个只是"本来能直接显示的格式多走一次后端转码"。

顺带收紧了 `ViewerPanel`：`needsPreview` 的口径是"Chromium 画不了这张图"，
**对视频/音频没有意义**（`preview.get` 对非图片一律返回 `null`）——此前它被无条件用于
所有媒体类型，取反后会直接把"能播的视频"变成"不可用"。现在只在
`media_type === "image"` 分支消费，由门禁断言。

## 元数据与抽帧管线

- ffprobe：文件索引时探测全量媒体信息，结果缓存进文件索引（存储形式属于实现期开放点）。
- ffmpeg：扫描期批量抽首帧，生成缩略图；同一抽帧结果可复用为感知哈希输入。
- 音频占位行（D11）不参与该管线；未知类型不入库。
- 外部进程调用必须有超时与错误降级（探测失败标记、抽帧失败用占位图）。

## 色彩参考语义

- 范围：仅图片。
- 自动提取：浏览时按需提取主色调/调色板并缓存；算法与色板数量属于实现期开放点。
- 手动调整：用户可调整/锁定色值，覆盖自动结果；存储在仓库内（`color_refs`），按仓库隔离。
- 用途：检索辅助、调色参考；不参与文件身份判定。

## 风险

- 捆绑 ffmpeg/libmpv 增大应用体积；发布与许可合规（LGPL 等）需在发布前确认。
- 媒体子进程 IPC 与原生渲染目标挂接是主要复杂度；必须防止面板销毁后句柄泄漏。
- 扫描期同步抽帧会拖慢扫描；需与任务进度、取消机制协同（见模块边界的长任务要求）。

## 实现期开放点（非架构决策）

- 媒体子进程 IPC 协议细节。
- 视频元数据在文件索引中的存储形式（JSON 列 vs 独立表）。
- 缩略图缓存位置与清理策略。
- ffmpeg 抽帧参数（帧位置、分辨率上限、编码格式）。
- 调色板提取算法与色板数量。**（2026-09-29 已定：色板固定 8 色，用户指定；算法仍为"缩放到 64×64 + 4 位量化 + 频率排序"。缓存带格式版本以便规模变化后自动重算——见 `docs/architecture/decision-checklist.md` 的 D81 与 `crates/hp-media/src/palette.rs`。）**
- libmpv 渲染目标与 Tauri 面板容器挂接的具体方案。

## 已知缺口：不支持的图片格式

> 完整的判定依据与实测矩阵见上文「图片格式支持边界」；这里只列**结论**，便于查阅。
> 这些格式**不索引、不显示**，且**不是本次能修的**——要支持必须引入新的解码依赖。
>
> **当前合计：6 类 / 21 个扩展名**（2026-10-16，D112 落地后复核）。对照：
> 已支持 **44 个**扩展名（进程内 22 + libheif 3 + `resvg` 2 + 仅 ffmpeg 17）。

| 缺口 | 扩展名 | 个数 | 阻塞点 |
| --- | --- | --- | --- |
| 相机 RAW | `dng` `cr2` `cr3` `nef` `arw` `orf` `rw2` `raf` `pef` `sr2` | 10 | 捆绑 ffmpeg **没有任何 RAW 静态图解码器** |
| JPEG XR | `jxr` `wdp` `hdp` | 3 | ffmpeg 无解码器；Windows 系统 codec 不可依赖（同 0019 对 WIC 的裁决） |
| 矢量 / 分层工程格式 | `xcf` `eps` `wmf` `emf` | 4 | ffmpeg 无解码器，且本身不是位图 |
| 扫描件二值压缩 | `jbig` `jbig2` | 2 | ffmpeg 无解码器 |
| Apple 图标 | `icns` | 1 | ffmpeg 无解码器（`ico` 支持） |
| WebP 2 | `webp2` | 1 | 实验格式，无解码器 |

> **SVG / SVGZ 已从此表移除**（D112，2026-10-16）：它曾以"**缩略图 / 调色板 / 感知哈希**
> 缺失（查看器显示不受影响）"的形式登记在这里，现已由进程内 `resvg` 栅格化补齐，
> 四项派生数据（缩略图 / 调色板 / 感知哈希 / 全分辨率预览）与位图同口径。
> **查看器显示**本就由 Chromium 原生渲染 `svg`；`svgz` 则走后端预览
> （白名单取反，见 §5 与 `previewUrl.ts`）。

> **判定方法本身值得记住**：不能只看 `ffmpeg -demuxers` / `-decoders` 的清单就下结论。
> `svg` 是**假阳性**（在解复用器清单里 → 误判"支持"）的来源，
> 而按扩展名 grep 又会把 **JPEG XL（解码器名 `libjxl`）** 误判成"不支持"，
> 唯一可靠的判据是**按本项目真实管线跑一遍**并检查产物。
