# RFC 0009：插件分发策略（分发通道 / 签名 / Python 核心）

状态：正式草案。本文承接 RFC 0004 的插件系统顶层决策，把「插件包如何被生产、签名、交付、安装、更新与回滚」固化为可实现的通道矩阵。本文记录用户已确认的方向（D38–D45）；实现期开放点不得反向修改这些决策。

## 已确认决策

1. **Rust 插件不使用源码分发**：要求用户侧编译不可接受，一律走二进制包（`.zip`）。
2. **Python 插件可以源码分发**：由「Python 核心」system 插件提供 Python 环境。该插件本身是**待办**。
3. **`system` 权限必须签名**：签名主体只能是**主线仓库构建人员**，当前仅 `ytmmi`。
4. **二进制包格式为 `.zip`**。
5. **WASM 运行时选 `wasmi`**。
6. **允许 `external-process` 插件自带原生依赖**（DLL、模型权重等）。
7. **插件来源由宿主按实际安装方式判定**，manifest 不得自称 `system`（RFC 0004 决策 17）。
8. 插件可创建**控件**，但控件标准必须先规范：`docs/spec/control-standard.md`。（**2026-09 修订**：插件控件类别「浮动控件」已取消，浮在布局之上的一层显示改由蓝图 `overlay` 容器承载，其显隐由蓝图规则决定。）

## 问题

现有实现只覆盖「本地目录 → 复制到版本目录」一条路径（`crates/hp-plugin-host/src/install.rs`），其余分发能力都缺位：

- `InstallSource::Git` 只接受**已克隆好的目录**，没有任何 git 拉取逻辑，也没有桥接命令可达；真正使用 git 需要用户自己有 git 客户端。
- 没有归档包通道，唯一封装原语是 `copy_dir`，无任何解包防护。
- ~~信任推导读取的是 **manifest 自称**的 `source.kind`（`crates/hp-plugin-host/src/trust.rs`），本地目录可自封 `system` 并解锁动态库（D4）。~~ → **已修（2026-09，缺陷 0008）**：`manifest.rs` 不再解析 `source`，`PluginManifest` 无来源字段，`effective_trust` 只接受宿主构造的 `HostSourceKind`（`trust.rs`）；注册表 `source_kind` 与 `trust_level` 同源于 `PluginInstaller::install_registry_row` 的一次宿主判定。
- `plugin.load` 是空壳，三种运行形态都没有执行体。

因此分发策略必须同时解决三件事：**通道**（包从哪来）、**来源判定**（谁说的算）、**运行环境**（装完能不能跑）。

## 分发通道矩阵

| 通道 | 交付形态 | 适用插件 | 更新方式 | 信任上限 |
| --- | --- | --- | --- | --- |
| 应用安装包 | 源码随仓库 + 安装期登记 | 系统插件、Python 核心 | 跟随应用版本 | `system`（随主线仓库构建，**仍须验签**） |
| git | 锁定 commit/tag 的仓库目录 | 源码可达的插件（Python 插件为主） | 手动检查 + 确认 | `community`，可提升 `trusted` |
| 归档包 | **`.zip`** + 分离发布的摘要文件 | Rust 插件、含原生依赖的插件 | 手动检查 + 确认 | `community`；有主线签名为 `system` |
| 本地路径 | 目录 | 开发调试 | 手动替换 | `local-dev` |

通道选择规则：

- **要编译的语言 → 归档包**。Rust 插件必须由作者预编译并打包（决策 1）。
- **解释型语言 → git 源码**。Python 插件源码即产物；前提是 Python 核心已安装（决策 2）。
- **纯计算/解析/UI 辅助 → WASM**。一个 `.wasm` 文件跨平台，体积小到可直接入库，是唯一能同时走 git 与归档包的形态。
- **随应用发布的 → 应用安装包**。系统插件与 Python 核心由主线仓库构建并随应用版本更新。

## 来源与信任判定

来源与信任必须分离，`effective_trust` 只接受宿主判定出的来源，不再读取 manifest：

```text
安装入口 → 判定 Provenance → 推导 TrustLevel → 写注册表
                    │
                    ├── AppBundle     : system  （随安装包登记 **且必须验签** plugin.sig，D40；随包不等于免签）
                    ├── Git{url,rev}  : community（请求 trusted 时用户显式提升并记录）
                    ├── Archive{sha}  : community（签名校验通过且签名者为主线构建者时 system）
                    └── LocalPath     : local-dev（永不提升）
```

宿主校验规则（安装时与加载时都要执行）：

- manifest 含 `source` 字段：**忽略**，不得参与判定；仅登记 `publisher` / `license` / `homepage` 等展示元数据。
- 声明 `dynamic-library` 但不满足 `system`/`trusted`：拒绝加载（RFC 0004 既有规则）。
- 用户投放到插件目录的插件包：即使 manifest 自称 `system`，也只能是 `community`（归档包）或 `local-dev`（目录）。

## `system` 等级签名

`system` 是唯一能解锁动态库与后续高权限能力的等级，因此必须有密码学凭据，而不是自证。

| 项 | 规定 |
| --- | --- |
| 签名主体 | 主线仓库构建人员，当前仅 `ytmmi` |
| 签名算法 | Ed25519（单文件公钥，便于内置与轮换） |
| 公钥分发 | 随应用内置；以**公钥指纹白名单**形式存储，指纹变更随应用版本发布 |
| 私钥保管 | 不得进入仓库、CI 日志、构建产物；建议离线保管 |
| 签名覆盖 | `plugin.manifest` + 包内全部参与加载的文件（`entry`、动态库、Python 入口、原生依赖） |
| 校验时机 | 安装时校验一次，加载时复核一次（防安装后被替换） |
| 校验失败 | 拒绝安装，或降级为 `community` 并要求用户显式确认；**不得静默提升** |
| 记录 | 任何信任等级提升/签名校验结果写入事件与操作记录 |

签名文件与摘要文件的落位（`plugin.manifest` 同级）：

```text
plugin-package/
  plugin.manifest
  plugin.sig              # 主线构建者签名（system 等级必需）
  SHA256SUMS              # 各文件摘要，与包一同校验完整性
  bin/ | lib/ | py/
  assets/
  README.md
```

- `SHA256SUMS` **只保证完整性与可复现**，不保证真实性：哈希与包放在同一页面时只防传输损坏。
- 真实性由 `plugin.sig` 提供；两者职责不得互相替代。
- git 插件的签名校验首期仍不强制（RFC 0004 决策 11），`system` 例外。

### `trusted` 与 `system` 的边界

签名是 `system` 的**独占凭据**，不等于「高信任等级都需要签名」：

- `system`：主线仓库构建者签名，无需用户判断，公钥随应用内置。
- `trusted`：**仍为用户自证**——用户显式提升并记录，不要求签名。它仍可解锁动态库（RFC 0004 决策 10 / D4），因此本等级的能力等价于「用户愿意为该作者承担进程内风险」。
- 后果：动态库插件的信任来源有两条——主线签名（可自动接受）与用户提升（必须显式确认，UI 应明示「该插件将在本进程内运行原生代码」）。
- 若后续要求 `trusted` 也签名，属于决策变更，需重开本 RFC 与 RFC 0004 决策 10；当前不做。

## Python 核心（待办）

目标：以 system 插件形态提供 Python 运行环境，使 Python 插件可以源码分发。

| 项 | 规定 |
| --- | --- |
| 插件类型 | `system`（随应用安装包分发，需签名，D40） |
| 运行形态 | 自身为 `external-process`；对外提供 Python 插件的**拉起与沙箱** |
| Python 运行时 | 内嵌或随包发布（不依赖用户系统 Python）；具体方式为实现期开放点 |
| 依赖管理 | 安装期由用户确认后获取，或随核心插件提供（**D20 只约束构建链本地化，不涉及运行期联网**；插件联网须按仓库授权 `network` 能力） |
| 隔离 | 每个 Python 插件独立进程；按仓库启用与能力授权照常校验 |
| 入口 | 插件包内 `entry` 指向 Python 脚本；原生依赖按决策 6 允许 |
| 默认信任 | Python 插件默认 `community`；不得因「只是脚本」而放宽能力校验 |

Python 插件的分发因此回到「源码可审计」的路径：用户能读到自己即将授权的代码，这弥补了二进制通道不可审计的短板。代价是依赖获取与版本漂移，必须由 Python 核心统一收敛（锁依赖清单、固定解释器版本）。

## 通道细节

### 应用安装包

- `plugins/system/` 是系统插件的**源码与打包输入**，不是运行时插件目录。
- 用户插件目录为应用数据目录下的 `plugins/`。**2026-09 已按上一条建议落地**：实现为 `app_local_data_dir()/plugins`（`%LOCALAPPDATA%`），并对旧 `app_data_dir()/plugins` 做**一次性无损迁移**（`apps/desktop/src-tauri/src/main.rs` 的 `resolve_data_dir`；`decide_dir` 保证只迁一次，`migrate_dir` 优先 `rename`、跨卷则递归复制，**失败回退旧目录**）。**注意**：`app_data_dir()` 下仍留有数据库等其它内容，见缺陷 `docs/issues/0012-databases-in-roaming-wal-risk.md`。
- 安装期（首次运行或版本升级后）把随包的系统插件登记进注册表；更新跟随应用版本，不走 `plugin.rollback`。
- **建议改到 `%LOCALAPPDATA%`**：Windows 的 Roaming 目录会同步，而插件与原生依赖可能数百 MB（对比 `external-cli/ffmpeg` 已约 200 MB）。

### git 通道

- 安装记录 `url` + 锁定 `rev`（commit 或 tag），写入版本目录的 `LOCK`。
- 浅克隆与「锁定任意 commit」冲突：需要 `fetch --depth 1 <sha>` 兜底，或记录可解析的 ref。
- 更新保留旧版本目录，回滚 = 目录切换，不依赖网络（D2 既有约定）。
- `LOCK` 增加 `mirror_url`：原 URL 不可达时仍可定位与手动重装。
- 私有仓库需要凭据支持，否则该通道对用户不可用。

### 归档包通道（`.zip`）

- 包根即插件包根（`plugin.manifest` 在 zip 顶层，或仅在唯一一层目录内，两种都要接受）。
- 安装流程：下载/选择 → **解包到临时目录**（含 D41 解包防护）→ 校验 `SHA256SUMS`（包内清单）→ 校验 `plugin.sig`（`system` 必需）→ 校验 manifest → 原子移动到 `<root>/<id>/<version>/`。
  - **必须先解包再校验**：签名与摘要覆盖的是**包内文件**，不解包无法逐文件核对。
  - **摘要双轨**：包内 `SHA256SUMS` 用于安装时逐文件核对（防传输损坏与包内不一致）；**发布侧另附一份摘要**（与包分离发布）才是真实性的补充凭据，两者都做。
- 解包防护（强制，缺一即视为漏洞）：
  - 拒绝绝对路径与盘符路径；
  - 拒绝任何含 `..` 的路径段；
  - 拒绝符号链接与目录联接（Windows junction）；
  - 限制解压后总大小与文件数，拒绝 zip 炸弹；
  - 统一大小写后检测同名覆盖（Windows 大小写不敏感）。
- 失败必须清理临时目录，不得留下半个版本目录。

### 本地路径通道

- 保持现状：复制到版本目录，信任等级固定 `local-dev`。
- UI 应改为「打开文件夹选择器」而不是手输路径（当前 `PluginPanel.tsx` 靠手输）。

## 版本目录与回滚

- 布局：`<plugin_root>/<plugin_id>/<version>/`，回滚即切回旧目录（D2 已确认，实现已具备）。
- **缺 `active_version`**：`plugin_registry` 无此列，更新是 upsert 覆盖（`crates/hp-store/src/global/plugin_repo.rs`），旧版本的 `manifest_json` 随覆盖丢失。
- 需要补：注册表增加 `active_version` 与 `updated_at`；每个版本目录保留自己的 manifest 副本，回滚与审计都能取到当时的清单。
- `plugin.rollback` 目前只返回目录路径，不切换活跃版本，必须改为原子更新注册表。
- 旧版本清理策略：保留最近 N 个版本、用户可手动清理；清理必须避开 `active_version`。

## 更新语义

- 不自动更新；用户手动检查并确认（RFC 0004 决策 5）。
- 更新前预检：新版本 `min_host_version` 高于当前宿主 API 时拒绝并说明原因，不得装完后才失败。
- 更新后注册表需记录来源版本，供审计与回滚。
- 更新失败必须保持旧版本可用（目录未切换即视为未更新）。

## 明确不做

- 完整插件市场与中心化 registry（沿用第一期范围外）。
- 自动后台更新。
- 跨平台二进制矩阵（当前产品范围为 Windows）。
- **禁止**插件自带安装脚本（`.zip` 内不得有需要执行的安装步骤）。

## 实现注意

- 归档包解压使用纯 Rust 实现以符合 D20，不引入原生依赖。
- `entry` 必须相对版本目录解析，禁止 manifest 指定任意命令。
- `external-process` 的原生依赖在 manifest 中声明；缺失即拒绝加载，不静默降级。
- 外部进程需要监督规则：崩溃重启次数与退避、连续失败 N 次标记不健康并广播 `plugin.error`（`docs/spec/commands-events.md`）。
- 平台差异只允许出现在宿主侧；插件包格式在 Windows 上唯一。
- 签名私钥不得进入仓库、CI 日志与构建产物。

## 与 tag 库扩展包的衔接

D36.1 把「tag 库扩展包是否经插件系统承载」延后到插件系统定案。本文给出可用结论供届时判断：

- 扩展包是**数据**而非代码，不得声明 `network`、`native.code`，也不应要求运行形态。
- 现有 `RuntimeKind` 只有三种运行形态，没有「纯数据包」档位；若经插件系统承载，需要新增数据包档位或另建通道。
- 现有约束可直接复用：来源由宿主判定、版本目录管理、回滚、`.zip` 归档与摘要校验、签名（若作为 `system` 数据）。
- 「应用级共享」与「插件启用是仓库级」的语义冲突仍未解决，属 D36.1 的讨论范围，本文不改变其状态。

## 开放点（实现期）

- Python 运行时的内嵌方式与体积预算。
- Ed25519 密钥轮换流程（多公钥并存过渡期）。
- 归档包是否需要增量更新（首期不做，仅记录）。
- 插件存储根目录迁移到 `%LOCALAPPDATA%` 的迁移策略。
- WASM 宿主导入函数的最终清单（见 RFC 0004「实现注意」）。
- Python 依赖锁文件格式与获取来源。
