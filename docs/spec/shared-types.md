# 共享类型生成策略

状态：正式草案。本文规定共享类型的生成与防漂移机制；具体工具选择属于实现期开放点。

实现状态（已落地）：采用方案 A —— 独立 `crates/hp-dto` 承载跨层 DTO，使用 `ts-rs` 生成；生成产物提交 git；`pnpm generate:types` 生成、`pnpm check:types` 做漂移校验。

## 1. 目标

`packages/shared-types` 由 Rust 类型生成前端 TypeScript 类型，作为 Tauri 命令/事件载荷与领域视图模型的单一事实来源，避免前后端手写重复类型导致漂移。

## 2. 单一事实来源（所有权）

- 命令请求/响应、事件载荷、领域视图模型（文件索引行、相册、tag、评分、色彩参考）的源类型放在 Rust 侧。
- 推荐方案：在 `hp-core` 中定义纯数据 DTO（不引入 Tauri/SQLite/fs 依赖），或建立独立 `crates/hp-dto` 专门承载跨层 DTO。
- 推荐采用 `hp-dto` 独立 crate：既能保持 `hp-core` 纯净，又能让 `hp-store`、`hp-scanner`、`hp-album` 等依赖同一套稳定 DTO。最终是否单独成 crate 属于实现细节，不影响"由 Rust 类型生成"的架构决策。

## 3. 类型清单

| 类别 | 示例 | 来源 crate |
| --- | --- | --- |
| 命令请求/响应 | `RepoOpenRequest`、`SourceMountRequest` | `hp-dto` |
| 事件载荷 | `ScanProgress`、`AiTaggingCompleted` | `hp-dto` |
| 领域视图模型 | `FileIndexRow`、`Album`、`Tag`、`Rating`、`ColorRef` | `hp-dto` |
| 插件 manifest/schema | `PluginManifest`、面板 schema 类型 | `hp-plugin-host` / `hp-dto` |
| 布局/配置类型 | `PanelLayout`、前端常量、面板注册表 | `packages/config` |

## 4. 生成机制

- 方案 A：`ts-rs` crate，直接从 `#[derive(TS)]` 标注的 Rust 结构体生成 `.ts`。
- 方案 B：Rust 侧导出 JSON Schema（如 `schemars`），再用 codegen 工具生成 TypeScript。
- 推荐：方案 A（`ts-rs`）——单一工具链、类型保真度高、与 Cargo 集成紧密；如后续需要跨语言契约再引入 JSON Schema 作为补充。最终工具选择属于实现期开放点。

## 5. 生成文件策略

- 每个生成文件头部必须标记来源 crate 与类型，示例：

```ts
// @generated by hp-dto (ts-rs) — DO NOT EDIT
// source: crates/hp-dto/src/repo.rs
// regenerate: pnpm generate:types
```

- 生成文件禁止手改；修改只改 Rust 源类型后重新生成。
- 推荐：生成产物提交进 git，CI 校验"重新生成后无 diff"以发现漂移；备选为构建时生成。提交与否属于实现细节。

## 6. 防漂移机制

- CI 步骤：运行类型生成命令，`git diff --exit-code` 校验生成产物与提交一致；不一致即失败。
- 版本策略：破坏性变更（字段删除/改名/类型改变）升 `shared-types` 次版本，并同步更新 UI 侧引用；新增字段保持向后兼容（可选字段）。
- 前端 `apps/desktop` 与 `packages/ui` 只 import 生成类型，不得手写同名字段结构。

## 7. 包布局角色

- `packages/shared-types`：生成的 DTO 类型；不知道任何 UI 业务。
- `packages/ui`：可复用面板组件、布局组件、设计 tokens；组件 props 可用 shared-types，但不反向依赖仓库业务。
- `packages/config`：前端共享配置、常量、面板注册表类型、布局类型（面向 UI 的结构，非跨层 DTO）。

依赖方向只允许向下：`apps/desktop -> packages/ui -> packages/shared-types`，以及 `apps/desktop -> src-tauri -> crates/*`（见 `docs/architecture/file-structure.md`）。

## 8. 实现期开放点（非架构决策）

- 生成工具最终选择（`ts-rs` 或其他）。
- 是否单独成 `hp-dto` crate，还是并入 `hp-core`。
- 生成产物提交 git 还是在构建时生成。
- 破坏性变更时的版本号粒度与 UI 同步流程。
